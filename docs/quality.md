# IO Probe 质量履历

当前版本：固件 **0.6.0** · 协议 v1 · 电脑端库 ioprobe 0.4.0 · 硬件 HPM5301EVKLite RevB
最后更新：2026-10-20

本文档记录三类内容：**待测试项目**、**未解决的问题**、**已关闭的问题**，以及每个版本的变更和验证情况。
新发现的问题按编号顺延追加，关闭时移到"已关闭的问题"，并注明在哪个版本关闭、怎么验证的。

状态说明：
- **待测**：还没做
- **阻塞**：缺设备或条件，暂时做不了
- **未解决**：已确认存在，还没修
- **已缓解**：用规避手段绕开了，根本原因没查明
- **已关闭**：已修复并验证

## 2. 未解决的问题

| 编号 | 问题 | 影响 | 规避方法 | 发现版本 | 状态 |
|---|---|---|---|---|---|
| Q01 | J1、J2 的 Type-C 缺 CC 下拉电阻（5.1 kΩ），C-to-C 线接 USB-C 主机口时不上电、不识别 | 用 C-to-C 线插 Mac / 笔记本的 USB-C 口无法使用 | 用 A-to-C 线，或在 USB-C 口加"C 转 A"转接头；彻底解决需在 CC1/CC2 各焊 5.1 kΩ 到地 | 0.3.0 | 未解决（硬件） |
| Q02 | 实际 SWCLK 正好 24.0 或 25.0 MHz 时，连接 STM32G0B1 大多失败（24 MHz 下 8/10 失败）；23.2 MHz、25.7–48 MHz 正常 | 用户设 24 / 25 MHz 时以前会连不上 | 0.6.0 固件选分频时跳过 23.5–25.5 MHz；原因待示波器排查（T09） | 0.5.0 | 已缓解 |
| Q03 | J3-37（PA30，丝印 USB0_PWR）接在 J1 的 VBUS 供电控制电路上，被拉低，不能当 GPIO；拉高可能往 J1 VBUS 输出 5 V | 少一个 GPIO；误驱动有风险 | 0.2.1 起从 GPIO 列表去掉，固件不碰它 | 0.2.0 | 未解决（硬件设计） |
| Q04 | J3-7：手册和丝印都写 PB15，但 J3-8 也是 PB15；SDK 里 J3-7 对应 PA02 | 这个脚的用途不确定，暂不分配 | 不使用；按 T08 量导通后再决定 | 0.1.0 | 未解决 |
| Q05 | 所有 IO 只支持 3.3 V，没有电平转换和保护 | 不能直接接 1.8 V / 5 V 目标；接错或静电可能损坏 HPM5301 | 只接 3.3 V 设备、务必共地；后续可加电平转换和 ESD 保护板 | 0.1.0 | 未解决（硬件） |
| Q06 | J3-29（nRESET）和 J3-31（GPIO）原本是 USB_ID / USB_OC 线，板上带上拉，可能还连着别的电路 | J3-31 悬空读到 1；若有其他负载，可能影响复位或 GPIO 行为 | 目前 G0B1 上复位正常；异常时把 nRESET 改到别的脚 | 0.2.0 | 观察中 |
| Q07 | 目标串口没有用 DMA：TX 轮询、RX 中断；电脑不读时 RX 缓冲（4 KB）满了会丢数据 | 高波特率或电脑处理慢时可能丢字节 | 1 Mbaud 以内使用；需要更高时加 DMA（见 T04） | 0.2.0 | 未解决 |
| Q08 | IO Probe 控制协议一次只处理一条命令，小命令往返约 86 µs，不支持批量 | AI 做大量小操作（如上千次 GPIO 翻转）时较慢 | 后续可加批量命令 / 脚本下发 | 0.1.0 | 未解决（功能限制） |
| Q09 | 单帧回复数据最多 4095 字节（请求 4096） | 大块 I2C/SPI 读需要拆成多次 | 电脑端库已做参数检查；后续可加大帧长 | 0.1.0 | 未解决（功能限制） |
| Q10 | DAP 的 `CPU_CLOCK` 是沿用 CherryDAP 的标定值（36 MHz），只影响 `DAP_Delay` 和复位时序这类软件延时的准确度 | 延时可能偏短或偏长；目前没发现实际影响 | 有示波器后重新标定 | 0.2.0 | 未解决（次要） |
| Q11 | SPI 模式下 SWCLK/SWDIO 由 SPI 外设占用，CMSIS-DAP 的 `DAP_SWJ_Pins` 只能读不能直接拉这两个脚 | 极少数依赖手动拉 SWCLK/SWDIO 的工具功能无效；OpenOCD 正常使用不受影响 | 无需处理 | 0.5.0 | 未解决（次要） |
| Q12 | macOS 上两个串口的名字按 USB 位置生成，不带接口名；电脑端库靠排序区分控制口和目标串口 | 理论上换系统或驱动后可能分错 | Linux / Windows 用接口号区分；macOS 实测正确 | 0.4.0 | 观察中 |
| Q13 | `.vscode/settings.json`、`.clangd`、`.mcp.json`、`flash.sh`、`hpm_env.sh` 里有本机绝对路径 | 换电脑要改路径 | `flash.sh` 和 `.mcp.json` 已支持环境变量覆盖；其余手动改 | 0.1.0 | 未解决（次要） |
| Q14 | I2C 全地址扫描约 105 ms，受驱动的地址应答重试次数影响 | 扫描偏慢 | 可调小重试次数 | 0.1.0 | 未解决（次要） |
| Q15 | 在线版规格书（Claude Docs）停在 0.2.1 / 0.3.0 前后的内容，本地 `docs/spec.md` 是最新的 | 读在线版会看到过时数据 | 以本地 `docs/` 为准，需要时再同步 | 0.3.0 | 未解决（文档） |

## 3. 已关闭的问题

| 编号 | 问题 | 原因 | 处理 | 关闭版本 |
|---|---|---|---|---|
| C01 | HPMicro 官方 macOS 工具链运行报 `Library not loaded: libisl.23.dylib` | 依赖 Intel 版 Homebrew 的库 | 改用 xPack riscv-none-elf-gcc 15.2（arm64 原生），cmake 加 `-DCUSTOM_TARGET_TRIPLET` | 环境搭建 |
| C02 | GPIO 设为输出后读回的电平和写入不一致 | 引脚在输出状态下默认不回送输入 | 所有 GPIO 打开 IOC 的 LOOP_BACK | 0.1.0 |
| C03 | PING 发 4096 字节返回 TOO_LONG | 回复里状态码占 1 字节，数据上限是 4095 | 协议说明写清上限，电脑端库提前检查 | 0.1.0 |
| C04 | HPMicro 的 macOS 版 OpenOCD 不支持 J-Link | 编译时没带 jlink 驱动 | 改用 SEGGER J-Link 软件烧录（`flash.sh`） | 0.1.0 |
| C05 | J3-37 推挽输出 1 读回 0 | 该脚是 USB0_PWR，被板上电路拉低（见 Q03） | 从 GPIO 列表去掉 | 0.2.1 |
| C06 | STM32G0B1 一直处于复位，halt 超时、外设寄存器读 0 | 目标板 NRST 接线错误（非产品缺陷） | 重新接线；排查方法写进 pinout.md | 0.3.0 |
| C07 | 固件一直以 `-O0` 编译，USB 和 SWD 性能只有一半 | SDK 把 `CMAKE_BUILD_TYPE=flash_xip` 当作 debug | CMakeLists 默认 `flash_xip` + `release`（`-O3`） | 0.4.0 |
| C08 | 大块数据往返慢（4 KB 回显只有约 0.8 MiB/s） | 固件逐字节处理、逐位 CRC；电脑端纯 Python CRC | 查表 CRC、`memcpy`、电脑端改 `binascii.crc_hqx`，提升到约 9.4 MiB/s | 0.4.0 |
| C09 | USB 序列号固定为 IOPROBE-0001，多块板会冲突 | 写死在描述符里 | 由芯片 OTP UUID 生成 | 0.4.0 |
| C10 | SWD 读速卡在约 260 KiB/s，换 SPI 也不提升 | 瓶颈是每个 512 B DAP 包的 USB 往返 | DAP 包长改为 1024 B | 0.5.0 |
| C11 | DAP 包长 2048 B 时 OpenOCD 报 `transfer count mismatch` | `DAP_Transfer` 回复计数只有 1 字节，OpenOCD 0.12 会塞超过 255 个传输 | 包长定为 1024 B（最多 255 个字） | 0.5.0 |
| C12 | GPIO 位操作 SWD 在 24 MHz 及以上连不上，且实际时钟和设定值不符 | 位操作速度和时钟标定的限制 | SWD 改为只用 SPI2，删除位操作 | 0.6.0 |
